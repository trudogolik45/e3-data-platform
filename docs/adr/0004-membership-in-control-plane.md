# OIDC отвечает за идентичность, Membership в Control Plane — за права

OIDC только говорит, кто пользователь: его идентичность — пара `iss` + `sub` из проверенного JWT. Права в Project хранятся в PostgreSQL Control Plane как Membership с одной Role (`Viewer` → `Editor` → `Admin`), а не в claims токена. PipelineRun запоминает Initiator (`initiated_by_user_id`), и перед каждой Publication Run Orchestrator заново проверяет его актуальный Membership в Project целевого Dataset. Так отзыв прав срабатывает посреди запуска, хотя токена пользователя у фонового процесса нет.

## Considered Options

- Роли в claims JWT (группы IdP): не нужна своя таблица, но права нельзя проверить без токена, а токен живёт дольше отзыва. Публикация посреди запуска шла бы по устаревшим правам. Отклонено.
- Проверять права только при создании PipelineRun: проще, но долгий запуск публикует в Dataset, куда у Initiator уже нет записи. Отклонено.

## Consequences

- Admin добавляет в Project только пользователей, которые уже входили: запись о User появляется при первом входе. Поиск по email — только по подтверждённому (`email_verified`), email не идентичность и не уникален между провайдерами.
- Organization доступа не даёт: в MVP пользователь к ней не привязан, доступ есть только через Membership в Project.
- Отзыв Membership не отнимает доступ к входным DatasetVersion, уже закреплённым в идущем PipelineRun: чтение проверяется только при создании запуска. Перепроверяется лишь запись.
- Нет нужной Role у Initiator при Publication — `Publish Dataset` уходит в `FAILED` с `access_revoked` без ретрая, дальше работает Fail-fast.
- Запуски, созданные до появления Initiator, принадлежат технической идентичности `legacy_migration` без Membership: их публикации не проходят проверку.
- Последнего Admin в Project нельзя удалить или понизить (`409`); проверка и изменение — в одной транзакции.
